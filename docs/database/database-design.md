# Database Design

## Overview

The Resume Analyzer SaaS uses **PostgreSQL** as its primary relational database.

The database is intentionally designed to be **simple**, **normalized**, and **easy to evolve**. Relational data is stored using standard tables and foreign keys, while AI-generated and parser-generated data is stored using PostgreSQL's `JSONB` data type.

The MVP contains only three core entities:

```
User
   │
   └───── owns ─────► Resume
                           │
                           └──── generates ───► Analysis
```

This design minimizes complexity while supporting future expansion.

---

# Design Goals

The database has been designed with the following principles:

* Keep the schema simple for the MVP.
* Normalize relational business data.
* Store flexible AI-generated structures using JSONB.
* Preserve historical analysis results.
* Prevent unnecessary PDF reprocessing.
* Support future feature expansion without major schema redesign.

---

# Why PostgreSQL?

PostgreSQL was selected because it provides:

* Strong ACID transaction guarantees.
* Excellent support for relational data.
* Native JSONB support for semi-structured data.
* Mature indexing capabilities.
* Excellent compatibility with Prisma ORM.
* Easy migration path for future scaling.

# Entity Overview

## User

Represents an authenticated user of the application.

Responsibilities:

* Authentication
* Account ownership
* Owns uploaded resumes

Relationship:

```
User
   │
   └── owns many Resumes
```

---

## Resume

Represents a resume uploaded by a user.

A Resume stores:

* Original uploaded PDF metadata
* Extracted plain text
* Parsed structured resume data

A Resume can be analyzed multiple times against different job descriptions.

Relationship:

```
Resume
   │
   └── has many Analyses
```

---

## Analysis

Represents a single comparison between a resume and a job description.

Each Analysis stores:

* Original job description
* Parsed job representation
* Snapshot of the resume used during analysis
* Rule Engine output
* AI-generated suggestions

An Analysis is immutable after creation.

---

# Entity Relationships

```
User
   │ 1
   │
   │ owns
   │
   ▼ *
Resume
   │ 1
   │
   │ generates
   │
   ▼ *
Analysis
```

Cardinality:

* One User can own many Resumes.
* One Resume belongs to exactly one User.
* One Resume can have many Analyses.
* One Analysis belongs to exactly one Resume.

# JSONB Usage

Several fields are intentionally stored as JSONB rather than normalized relational tables.

## structuredResume

Generated by the Parsing Module.

Contains the normalized representation of the uploaded resume.

Example sections include:

* Personal Information
* Education
* Experience
* Skills
* Projects
* Certifications

---

## parsedJob

Generated by the Job Description Parser.

Contains extracted job information such as:

* Required skills
* Preferred skills
* Experience requirements
* Education requirements
* Responsibilities

---

## resumeSnapshot

Stores a complete copy of the parsed resume used during analysis.

This ensures historical accuracy if the user uploads a newer version of the resume later.

---

## analysisResult

Stores the final output produced by:

* Rule Engine
* AI Suggestion Engine

Typical contents include:

* Overall match score
* Section scores
* Matching keywords
* Missing keywords
* AI feedback
* Improvement suggestions

---

# Why JSONB Instead of Tables?

These structures change frequently as the product evolves.

Using JSONB provides several advantages:

* Avoids frequent database migrations.
* Allows the AI output format to evolve.
* Simplifies parser development.
* Preserves complete analysis results.
* Reduces unnecessary relational complexity.

Business entities remain relational, while AI-generated documents remain document-based.

# Index Strategy

The following indexes are used to improve query performance.

| Table    | Index          | Purpose                       |
| -------- | -------------- | ----------------------------- |
| users    | email (UNIQUE) | Login lookup                  |
| resumes  | userId         | Fetch user's resumes          |
| analyses | resumeId       | Fetch analysis history        |
| analyses | createdAt DESC | Display newest analyses first |

---

# Cascade Delete Rules

The database enforces ownership through cascading foreign keys.

Deleting a User will automatically delete:

* All Resumes
* All Analyses

Deleting a Resume will automatically delete:

* All Analyses associated with that Resume

Uploaded PDF files are deleted by the application layer during the deletion process.

---

# Timestamp Strategy

Every entity stores timestamps using PostgreSQL `TIMESTAMPTZ`.

Fields:

* createdAt
* updatedAt

All timestamps are stored in UTC to ensure consistency across different time zones.

---

# Historical Snapshot Strategy

Analyses are intentionally immutable.

When an Analysis is created, the system stores a snapshot of the parsed resume rather than referencing the live resume data.

Benefits:

* Previous analyses remain accurate.
* Resume updates do not modify historical results.
* Users can compare analyses across different resume versions in future releases.

---

# MVP Design Decisions

## One Resume → Many Analyses

A resume can be analyzed against multiple job descriptions.

This avoids repeated uploads while allowing users to tailor their resume for different roles.

---

## Resume Parsing Happens Once

The uploaded PDF is parsed only during upload or replacement.

The extracted text and structured representation are stored permanently.

Future analyses reuse this data without reparsing the PDF.

---

## Analysis Stores Complete Results

Every analysis stores its complete output.

The system never recalculates previous analyses when viewed.

This guarantees consistency and improves performance.

# Future Expansion

The current schema intentionally remains small.

Future versions may introduce additional entities such as:

* CoverLetter
* Portfolio
* SavedJob
* InterviewSession
* UserPreferences
* AIUsageLog
* Subscription

These additions can be introduced without requiring major changes to the existing database design.

---

# Summary

The database follows a hybrid relational/document approach.

* Relational tables manage ownership and business relationships.
* JSONB stores parser-generated and AI-generated structures.
* Historical analyses remain immutable.
* Resume parsing occurs only once per upload.
* The schema prioritizes simplicity while remaining extensible for future growth.
